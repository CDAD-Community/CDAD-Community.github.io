Quick User Manual

You define the intent. CDAD protects the intent. AI accelerates implementation.

Leer en español View original Markdown
Golden rule: AI may analyze, propose and execute; authority over governed decisions remains human.

1. The complete flow

CDAD makes governance part of the normal workflow, so users do not have to manually manage every governance artifact.

YOU define → delegate → review → accept/reject
             ↓
AGENT analyzes → implements what is allowed → proposes when needed
             ↓
CDAD records decisions → updates context → protects what was approved

Routine implementation: delegate. Governed decision change: Change Request → Proposal → human review → acceptance → ADR/context.

2. First use: Bootstrap

Prepare the design

Keep an initial design document in the project root with the vision, objective, main functionality, architecture, technology stack, constraints and known decisions. It does not need to be perfect, but it must clearly represent what you want to build.

Incorporate CDAD

Give the ADE this URL:

https://github.com/CDAD-Community/cdad-bootstrap

Then ask:

Clone/incorporate CDAD Bootstrap into this project.
Inspect the project and use my initial design document
as the source for performing the CDAD Bootstrap.
Do not invent decisions; if information is missing, ask me.

The agent should inspect the project, identify the source document, detect conflicts, avoid guessing, map the design into CDAD artifacts and show you the result.

3. The two confirmations

A. Does this design represent what I want to build?

If not, correct the design and review it again. If yes, explicitly confirm it.

B. Did CDAD correctly represent my solution?

Review the vision, architecture, stack, principles, constraints and glossary. Correct anything that is wrong before freezing.

These are different decisions and both matter.

4. Review the workspace and Freeze

After Bootstrap you will find files such as AGENTS.md, CHANGE-REQUEST.md, SOURCE-BRIEF.* and a cdad/ directory containing context, ADRs, proposals and scripts.

The quick architecture map is:

cdad/context/stack.md

Once the context is confirmed:

cdad/scripts/cdad-freeze.sh

After Freeze, the agent must use the governed context as its source of truth and must not modify it directly. Protection should not rely only on an agent promise.

5. Normal development: delegate

Once the context is frozen, delegate work within the established boundaries:

Implement this functionality according to the governed CDAD
context. Do not change architectural decisions.

A Change Request is not needed for a bug fix, unit test, already-defined endpoint, refactor without a governed decision change or logging improvement.

6. When to use CHANGE-REQUEST.md

Use it when changing a governed decision: database, cloud platform, framework, architectural pattern, integration, constraint, security or deployment decision, or when introducing a major component.

Explain what you want to change, why, the trigger, scope, impact, risks, alternatives and priority. Then ask the agent:

Process the change request.

7. Proposal and human decision

The agent generates a Proposal describing the current decision, requested change, proposed change, reason, impact, risks, alternatives and affected context elements. A Proposal is not an automatic decision.

Your decisionResult
AcceptThe change may proceed through the governed process.
RejectThe architecture is not changed.
Request changesThe agent revises and completes the Proposal.

Never accept a Proposal simply because AI generated it. Review what changes, why it changes, impact, risks and alternatives.

8. ADR, context and map

An accepted Proposal that represents a new architectural decision must be recorded as an ADR:

Proposal → human approval → ADR → context/map → implementation

The architecture map must follow the decision. Do not edit stack.md directly to bypass the process.

9. What not to do

  • Do not directly edit frozen governed context.
  • Do not create copies to bypass protection.
  • Do not disable the guardrails.
  • Do not create a Proposal for every line of code.
  • Do not accept a Proposal without reading it.

10. Quick checklist

  • I prepared or defined the initial design.
  • I ran Bootstrap and confirmed the design.
  • I reviewed and confirmed the generated context.
  • I ran Freeze and checked the protection.
  • I delegate routine work without changing decisions.
  • I use CHANGE-REQUEST.md for governed changes.
  • I review and decide every Proposal.
  • I keep ADRs, context and the architecture map consistent.
